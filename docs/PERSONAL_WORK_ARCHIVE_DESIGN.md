所属产品：AIWorkSpace  
当前统一产品版本：`2.0.0`  
目标：在不影响正在使用的 2.0 的前提下，增加个人工作档案，并让工作记录与现有任务/步骤形成双向关联。

## 1. 已确认的产品原则

1. 个人工作档案是 AIWorkSpace 的内置模块，不是独立软件。
2. 版本号、更新机制、数据目录、项目、任务、步骤和用户体系均继承工作台；不建立独立模块版本。
3. 当前统一版本为 2.0.0。新功能成熟后作为工作台下一次统一功能版本发布，建议目标为 2.1.0；在此之前不改变 2.0.0。
4. 工作记录描述已经发生的事实；任务描述未来需要完成的独立工作；任务步骤描述某个任务内部的子行动。
5. 一次输入可以同时形成工作记录和后续任务/步骤，二者以来源关系关联，不是重复数据。
6. 允许 ChatGPT 云端产品处理个人档案；**不使用 OpenAI API 或任何模型 API，不产生模型 API 费用**。
7. ChatGPT 与 Google Drive 的双向数据通道此前已多次完成端到端验证。本阶段沿用既有通道，不重新论证其可行性。
8. 个人档案仅本人使用；不开放团队访问。
9. 不影响 AIWorkSpace 2.0 的现有使用；新功能在隔离分支和虚构测试数据中开发。
10. 历史事实、原始输入和证据必须可追溯；AI 不得虚构工作、结果或量化业绩。

### 2.2 当前数据结构

现有程序使用本机 Python 标准库服务，数据放在用户指定的 `--data-dir`，并通过 Google Drive 桌面同步。当前核心数据是追加式 JSON 事件文件：

| 目录 | 现有用途 |
|---|---|
| `events/` | 任务创建和更新事件 |
| `project_events/` | 项目创建和更新事件 |
| `step_events/` | 任务步骤创建、更新和排序事件 |

现有规则和能力：

- 任务状态：`todo`、`doing`、`blocked`、`done`。
- 任务字段：标题、状态、主要/关联项目、负责人、优先级、截止日期、计划日期、下次跟进日期。
- 任务步骤：独立 STEP ID、独立 revision、最多 100 步；步骤有标题、状态和顺序。
- 项目、任务、步骤分别有自己的事件流。
- 事件使用唯一 event_id、base_revision 和追加式写入。
- 写入先落临时文件，再以硬链接原子发布；目标已存在时拒绝覆盖。
- reducer 检测重复 event_id、同 revision 冲突、缺失父任务、部分同步及排序冲突；写入冲突返回 409。
- 旧任务没有项目或步骤字段时可以正常读取，缺失字段使用安全默认值；旧事件不需要批量重写。
- 任务或步骤完成状态必须由用户明确确认，ChatGPT 不得自行写入 done。

当前主要 API：

- `GET /api/tasks`：读取工作区任务、项目和步骤。
- `POST /api/tasks`：创建任务。
- `POST /api/tasks/{task_id}/update`：更新任务。
- 项目和任务步骤分别使用独立 API 路由。

现有任务/步骤模型没有专门的工作日志正文、会议记录、实际行动描述或成果证据字段。因此不应把工作日志塞进任务标题，也不应把每条工作日志伪装成任务步骤。

## 3. 统一业务模型：工作事实与未来行动

### 3.1 三类对象

| 对象 | 记录什么 | 是否有任务状态 |
|---|---|---|
| 工作记录 Work Record | 已发生的工作、会议、沟通、决策、问题、措施和结果 | **没有** |
| 任务 Task | 需要独立跟踪并产生交付结果的未来工作 | 沿用现有任务状态 |
| 任务步骤 Step | 某个任务内部的子行动，单独跟踪价值不足以成为任务 | 沿用现有步骤状态 |

工作记录不是任务，不进入待处理/进行中/已完成看板。AI 收件箱可以有“待整理/待确认/已整理”等**处理状态**，但这不是工作本身的状态。

### 3.2 示例一：会议产生后续行动

原始输入：

“今天跟几个部门开会，讨论了新系统上线的事情，发现采购和生产的数据接口还需要调整。”

AI 应形成：

**工作记录**
- 参加跨部门会议。
- 讨论新系统上线。
- 识别出采购与生产的数据接口需要调整。
- 发生日期按用户当地时间记录。

**未来行动**
- 如果已有“新系统上线/数据接口”任务：优先更新该任务，或在其下新增有独立执行意义的步骤。
- 如果没有对应任务，且接口调整有独立交付结果：创建一个任务，并关联现有项目。
- 如果只是需要在某个既有任务中做一个小操作：增加任务步骤。
- 如果“需要调整”只是初步讨论、责任和行动尚不明确：保存工作记录，询问是否需要建立任务。

工作记录与任务通过稳定 ID 关联。

### 3.3 示例二：沟通索要资料并产生 PPT 任务

原始输入：

“催促市场部要来公司介绍资料，接下来就改造编制公司 PPT。”

AI 应形成：

**工作记录**：已联系市场部，催要公司介绍资料。

**后续任务**：更新/编制公司介绍 PPT。

**前置条件**：等待市场部提供资料。

如果已有公司 PPT 改版任务，更新原任务或增加步骤，不重复创建。

### 3.4 任务/步骤判断规则

AI 必须先查询当前项目、任务和步骤，再决定写入：

1. 已经发生的事情进入工作记录。
2. 现有任务的下一步小操作进入任务步骤。
3. 已有任务的新进展更新原任务，不新建重复任务。
4. 有独立交付结果、需要独立跟踪的新工作，才创建任务。
5. 只有想法或不确定行动时，先保留记录；必要时询问。
6. 不为每个动词创建任务，不把会议讨论的每个议题都拆成任务。
7. 不擅自推断负责人、优先级、截止日期；日期不明确时留空。
8. 保留现有“任务/步骤完成必须用户明确确认”的规则。用户在 ChatGPT 叙述完成事实时，可以形成工作记录；若要改变现有任务的 done 状态，仍按既有人工确认规则处理。
9. 一条工作记录可以关联多个任务/步骤；一个任务也可以关联多条工作记录。

建议的关系类型：

- `derived_action`：该工作记录产生了这个后续任务/步骤。
- `progress_on`：该工作记录描述了这个任务的阶段进展。
- `result_of`：该工作记录记录了这个任务产生的结果。

## 4. 不使用 AI API 的工作方式

### 4.1 ChatGPT 入口

用户在 ChatGPT 手机或电脑端明确要求记录时：

1. ChatGPT 读取必要的现有工作记录、项目和任务。
2. 保存原始输入来源。
3. 分析已发生事实和未来行动。
4. 检查已有任务/步骤，避免重复。
5. 写入标准工作记录及必要的任务/步骤事件。
6. 写入工作记录与任务/步骤之间的关联。
7. 返回实际写入结果和稳定编号。

只有工具确认写入后才报告成功。失败时保留可重试状态，不虚报。

### 4.2 AIWorkSpace 快速记录入口

用户在工作台随时输入时：

1. 工作台立即把原始内容写入本地数据目录的工作档案收件箱。
2. Google Drive 按既有机制同步。
3. ChatGPT 在用户触发“整理工作档案收件箱”等指令时读取待处理内容。
4. ChatGPT 执行语义整理、去重、任务/步骤判断，并写回标准记录和关联。
5. 工作台显示整理状态和结果。

工作台本身不运行模型推理。没有 AI API 时，不能宣称本地输入一提交就已经完成后台 AI 理解。

### 4.3 工作台任务/步骤自动采集

工作台可以不依赖 AI 地识别并收集有意义的任务/步骤事件，作为 ChatGPT 后续整理的来源。

建议只把以下事件作为候选来源：
- 用户将任务/步骤状态改为进行中或受阻。
- 用户明确确认任务/步骤完成。
- 有明确实际进展的步骤更新。
- 后续经用户确认的其他业务事件。

默认不把普通任务创建、排序、刷新、标题小修、日期/负责人调整等所有系统事件都变成工作日志，避免噪音。

任务创建通常代表未来计划，不代表已经完成的工作。若任务由某条工作记录触发，应保留来源关联，避免该任务再次被自动提取成一条重复工作记录。

### 4.4 周期总结与无人值守边界

每日简短回顾、每周和每月深入总结由 ChatGPT 产品执行并写回工作档案。

不使用 API 的前提下：
- 用户主动触发总结可以实现。
- 可以利用 ChatGPT 产品内可用的计划任务/提醒能力提示用户回顾。
- **计划任务能否在无人值守时调用 Google Drive 连接器并写回总结，必须按实际产品能力单独验证；在验证前不承诺后台自动完成。**
- 若计划任务无法访问连接器，退化为定时提醒 + 一键触发 ChatGPT 整理，不增加 API 费用。

## 5. 新增数据设计（增量、追加式）

所有新数据放在现有 `--data-dir` 下，不放入程序目录或 GitHub 仓库。

建议目录：

```text
AIWorkSpaceData/
  events/                 # 现有任务事件，不改写
  project_events/         # 现有项目事件，不改写
  step_events/            # 现有步骤事件，不改写
  work_archive/
    inbox/                # 原始输入和待整理来源引用
    record_events/        # 标准工作记录的创建/修订事件
    review_events/        # 日/周/月总结及其版本
```

### 5.1 收件箱来源

人工输入保存原始文本、捕获时间、可识别的发生时间、来源渠道及附件引用。

工作台任务/步骤采集保存来源引用（目录、event_id、task_id/step_id、revision），不复制或改写原任务事件。

原始输入先保存；AI 处理失败、断网或连接器暂不可用时不能丢失。

### 5.2 标准工作记录

每条记录有独立稳定 ID，建议字段：

- record_id
- occurred_at：工作发生时间，含明确时区/偏移
- captured_at：实际录入时间
- title
- summary / description
- category
- project_id（可空）
- source_ids
- evidence_refs
- action_links
- facts：已确认事实、问题、行动、结果
- tags
- revision
- created_at / updated_at

字段按实际内容填写，不强制补齐，不允许 AI 编造。

记录事件采用独立 event_id 和 base_revision，追加式保存；修改通过新事件表达，原始来源不覆盖。

工作记录内部 record_id 使用独立命名空间，不复用 TASK/STEP ID；用户看到的显示编号遵循第 12 节统一规则。

### 5.3 工作关联

`action_links` 至少支持：

```json
{
  "target_type": "task",
  "target_id": "TASK-...",
  "relation": "derived_action"
}
```

也支持 `target_type=step` 及 `progress_on`、`result_of`。

关联由工作记录侧保存；工作台任务详情可反向查询关联记录。必要时再增加轻量关联事件，不复制任务/步骤正文。

### 5.4 证据文件

工作记录关联 Google Drive 中的原始文件，不默认复制附件。

保存文件 ID、名称、类型、所在位置及可用的版本/修改时间信息；文件移动或删除后能提示链接失效。

附件正文不默认全部发送给 ChatGPT；只有用户明确要求分析时才读取必要内容。

### 5.5 总结

日/周/月总结保存：
- summary_id
- period_type / period_start / period_end
- generated_at
- included_record_ids / source_ids
- summary_content
- revision
- 是否经用户修改/确认

总结属于可重生成的派生材料，不覆盖原始工作记录。

## 6. 与现有任务模型的兼容方式

1. 不改写现有 `events/`、`project_events/`、`step_events/` 文件。
2. 不批量迁移或重编号现有 TASK、PROJECT、STEP。
3. 新模块通过只读方式读取现有工作区，必要时在新增工作记录中保存关联 ID。
4. 新数据只写入 `work_archive/` 新目录。
5. 旧版没有 `work_archive/` 时，读取结果按空档案处理，不报错。
6. 新版读取历史任务时，继续使用当前 reducer 的默认值和冲突规则。
7. 若后续需要在任务/步骤事件中加入来源元数据，只能使用可选、向后兼容字段；旧事件必须继续有效，且需先加入兼容性测试。
8. 新版不得在迁移时覆盖或删除原始事件。优先采用“无需迁移、按需建立关联”的方案。
9. 更新器只更新程序白名单，不触碰 `--data-dir`。新增档案目录必须继续处于数据目录保护边界内。
10. 如未来确需迁移，先备份完整 data-dir，在副本执行迁移，逐条核对数量/ID/哈希，并提供失败回滚；未经用户明确批准不得操作实际数据。

## 7. 隐私和费用

- 档案存放在用户自己的私有 Google Drive 数据目录中。
- 不向团队或其他用户开放。
- 不把真实档案、附件、Drive 私有文件 ID、个人资料写入 Public GitHub。
- ChatGPT 云端处理是用户已允许的方式；这不等于数据只在本机。
- 不使用 OpenAI API 或其他模型 API，不新增 API key、服务账号或按量模型费用。
- 不增加未经批准的付费云服务。
- 普通文件同步/连接器操作沿用已有授权和路径。

## 8. 页面与交互

个人工作档案是 AIWorkSpace 的一个一级模块，建议内部页面：

1. 工作档案首页：快速记录、今日记录、待 AI 整理数量、近期总结。

## 12. 任务与工作记录的用户显示编号

### 12.1 内部主键与显示编号分离

当前任务使用 `TASK-<32位UUID>` 作为内部规范 ID。该 ID 已被任务事件、步骤关联、项目关联、API 路由和历史文件引用，不应直接替换或批量迁移。

建议增加用户显示字段 `display_id`：
- 内部 `task_id` 保持原样，继续作为唯一数据主键。
- 页面、搜索结果、ChatGPT 对话和复制操作优先使用短显示编号。
- 任务事件、步骤事件、项目关联和 API 写入仍使用内部规范 ID；ChatGPT 通过任务读取结果将显示编号解析为内部 ID。
- 新任务在创建时生成并持久化显示编号；直接通过 Drive 写入任务事件时也必须遵守同一格式及唯一性检查。
- 旧任务不改写原始 JSON。读取层根据原始 task_id 和创建时间生成确定性的历史显示编号；缺失创建时间时使用稳定的 legacy 形式。
- 如果检测到显示编号重复或无法可靠生成，必须明确提示冲突并阻止错误映射，不能静默指向任意任务。

### 12.2 建议格式（具体短码长度待用户最终确认）

| 对象 | 建议格式 | 示例 |
|---|---|---|
| 行动任务 | `T-YYMMDD-XXXXXXXX` | `T-261102-7K4M2P9Q` |
| 工作记录 | `R-YYMMDD-XXXXXXXX` | `R-261102-3M8K6P2Q` |

- `T` 表示 Task，`R` 表示 Record；两者共享日期与短码规则。
- 短码建议使用大写 Crockford Base32 字符集，排除容易混淆的字符。
- 不采用每日递增流水号作为唯一来源，避免依赖中心计数器和同步顺序。
- 生成时检查当前工作区已有显示编号；冲突时重新生成或扩展短码，并在事件流中保持编号稳定。
- 该显示编号不是 event_id；event_id 仍只用于底层追加事件的唯一性。

### 12.3 任务详情复制

- 详情抽屉显示短显示编号；编号本身可点击，旁边另有复制图标。
- 点击任一位置复制同一个 display_id；成功时显示轻量反馈，失败时给出明确提示，不假报成功。
- 复制逻辑不触发任务更新或新增事件。
- 搜索支持短显示编号精确匹配；AI 根据读取结果将显示编号映射到内部 task_id 后再写入。

### 12.4 历史错误分类的显式转换

对于已经存在、实际属于工作事实而非未来行动的旧 TASK：
- 不自动推断、不批量迁移。
- 用户明确确认后，创建一条新的工作记录，保存原任务 ID 作为来源和转换关联。
- 原任务事件文件保持不变；转换完成后在 UI 中明确显示其已转为工作记录/历史来源，避免同时作为待办重复展示。
- 具体“原任务如何从行动视图隐藏”须在 M2 实现前设计，不能通过伪造 done 或直接删除来解决。

## 14. 详情抽屉遮罩关闭规则

当前 UI 已有 `drawer-backdrop` 外层容器和 `closeTaskDetail()` 未保存保护函数，但没有遮罩点击监听。实现时：
- 仅当点击事件目标就是 backdrop 本身时关闭；点击抽屉内部的按钮、表单或内容不关闭。
- 调用现有 `closeTaskDetail()`，不另写绕过草稿保护的关闭路径。
- 如果未保存修改确认被用户取消，抽屉必须保持打开，内容不丢失。
