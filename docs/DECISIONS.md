# AIWorkSpace｜重要决策

日期：2026-10-27 起持续维护。只记录已确认的选择，以及首版正在验证的技术方向。

| 编号 | 决定 | 原因 / 状态 |
|---|---|---|
| D001 | AIWorkSpace 是全新独立项目，不继承旧项目代码或测试结论 | 简单从零开始 |
| D002 | 第一版只验证 ChatGPT 与网页的双向任务闭环 | 避免一次性开发过多功能 |
| D003 | 先个人使用，设计上保留未来团队扩展可能 | 先解决实际个人工作 |
| D004 | 优先 Google Drive 与现有 Windows 电脑，不默认增加付费云服务或 AI API | 跨设备、控制费用 |
| D005 | 用户已确认的需求统一维护于 `REQUIREMENTS.md` | 防止对话切换丢需求 |
| D006 | GitHub Markdown 文件作为跨对话/跨 AI 开发记忆；新 AI 必须主动读取和核实 | 项目可持续交接 |
| D007 | 本仓库 Public，绝不上传实际业务数据、个人隐私、密钥、授权凭证及敏感链接 | 防止公开泄露 |
| D008 | ChatGPT 负责开发、自测和维护；Codex 默认仅做独立验收；任务完成由用户手动确认 | 职责与权限清晰 |
| D009（核心链路已实测） | 首版采用 Python 标准库的 Windows 本机网页服务、Drive 桌面同步及每次追加独立 JSON 事件文件；事件发布必须原子且禁止覆盖，HTTP 必须校验本机 Host | 原两项 P2 已由 Codex Linux 独立复验通过；Linux/Windows CI 各 23/23 PASS；公司 Windows 电脑实测硬链接、Host 防护、双向同步、断网恢复、刷新持久性及旧版本写入保护。长时间稳定性尚未专项验证 |
| D010 | 当前阶段只部署和验收一台公司 Windows 电脑；不把第二台电脑并发测试列为交付门槛 | 用户明确当前只在公司电脑运行。重点验证单机服务与 Drive 桌面同步目录、ChatGPT 通过 Drive 连接器的读写闭环 |
| D011 | 验收用事件文件移入 `events/_archive_test_events_20261029` 子文件夹归档，不删除、不改写原始 JSON | 应用只读取 `events` 根目录的 JSON 文件；归档子目录保留证据但不进入日常任务列表。桌面同步后须刷新网页确认 |
| D012 | 暂缓远程访问；先完成 AIWorkSpace 产品功能，之后再基于届时的最新稳定版本补充远程访问 | 当前阶段不修改 M2/M3.1 的 Host/Origin 安全限制，不部署 Tailscale 远程入口；避免产品功能开发期间增加额外架构与验收范围 |
| D013（M3.3 实现方案） | 执行步骤使用独立 `step_events/` 追加式事件流；每步有独立 STEP ID 与 revision，步骤顺序使用任务级完整 ID 列表事件单独维护 | 步骤编辑不增加父任务 revision 冲突；顺序调整一次写入一个完整事件，避免多文件交换产生半完成排序；兼容 Drive 延迟同步，旧任务无需迁移 |
| D014（M3.3 部分同步保护） | 若当前生效的步骤排序事件引用了本机尚未收到创建事件的 STEP ID，必须标记排序不完整、暂停网页排序并由 API 返回 409；等待缺失创建事件同步后再恢复原排序 | 不得从当前可见步骤推导“完整排序”，不得猜测隐藏步骤的位置或静默丢弃其引用；保留原排序事件，避免 Drive 延迟同步造成数据丢失 |
| D015（M3.3 事件身份冲突保护） | `step_events/` 内同一 `event_id` 若对应不同内容，必须冻结所有受影响的步骤/排序流；冲突变体不得因 `base_revision` 连续而被当作有效事件应用 | 事件身份唯一性独立于 revision 连续性；排序冲突时保留候选和最后无冲突前缀，API 拒绝后续排序写入，其他无关步骤及合法不同 ID 连续事件不受影响 |
| D016（M3.4 首版只读分类与搜索） | 首页总览/筛选以现有 `GET /api/tasks` 状态在浏览器只读计算。本人需从现有负责人中显式选定；未配置不猜测。没有审核/决策字段时展示“不可自动识别”，不伪造 0；日期按本机日历，临近到期为今天到第 7 天（含），过期/受阻/冲突可重叠其他分类。筛选不改任务事件 | 优先交付低风险、可解释的个人工作台视图；避免用日期、优先级或负责人推断尚未建立的审批和身份事实，保留以后经用户确认扩展模型的空间 |
| D018（成功保存后推进草稿基线） | 每个编辑器成功保存时，必须把 watcher 的 clean baseline 更新为该次请求实际成功提交的快照，并立即与当前表单值重新比较；不得只从 dirty 集合删除表单。即使保存期间产生新输入，基线也要推进到已提交快照，新输入继续 dirty；兄弟草稿阻止重绘时同样适用 | 列表重绘可能被其他编辑器的未保存草稿阻止；旧 clean baseline 若未推进，会让用户改回保存前旧值时误判干净并在整页刷新时丢稿。任务与步骤编辑共用该规则 |\n| D017（浏览器离开页面草稿保护） | 所有未保存任务/步骤草稿必须通过 `beforeunload` 触发浏览器原生离开确认；只有存在实际 dirty 状态时提示，保存成功或恢复干净快照后清除；取消离开必须保留页面与输入。草稿快照必须按值比较，不能用新对象的引用相等判断 | 页面内刷新/筛选确认无法覆盖 F5、关闭标签页或导航离开；防止未保存输入静默丢失；第二轮实测发现新建任务快照每次新建对象，已改为 JSON 序列化值比较，避免字段恢复原值后误报 dirty |

| D019（内置软件更新中心） | 工作台显示语义版本与构建 SHA；更新源固定为公开仓库 yudacheng666/AIWorkSpace 的 main。网页检查后由用户点击一键更新；更新包仅安装 app.py、updater.py、VERSION、web/index.html，使用独立 helper 停止/重启服务。更新前备份程序，校验 GitHub commit、ZIP 完整性/路径/符号链接及文件清单；新版本启动失败自动回滚。任何更新操作必须与 --data-dir 隔离，禁止接触任务/项目/步骤事件数据 | 用户希望首次下载安装后不再反复从 GitHub 手动下载。固定源、白名单文件、独立备份、数据目录隔离和回滚降低一键更新风险；不增加云服务、Token 或远程访问。Windows 实机自动重启和真实数据隔离需单独验收后才可部署 |

| D020（Windows 更新端到端验收） | 软件更新功能的 Windows 关键链路由 GitHub-hosted Windows Runner 在隔离临时安装目录、虚构 data-dir 和真实 Chromium 浏览器中执行真实 app.py + updater helper；只 mock 固定官方 GitHub API/raw/zipball 响应，其他外部网络 fail-closed。必须覆盖网页一键更新成功、旧服务退出、新服务原端口/data-dir 重启，以及新版本启动失败后的旧程序/旧服务回滚和数据 SHA 不变 | Codex Cloud 当前仅有 Linux 执行环境；GitHub Windows Runner 可提供可重复、无公司数据风险的原生 Windows 验收。stub helper 测试不能代替真实应用网页链路；真实 GitHub main 发布下载需合并后另行隔离验证 |

| D021（测试去重与风险分流，2026-10-30） | GitHub Actions 为默认自动回归入口；Codex 仅对 CI 无法充分覆盖的中高风险场景作增量独立验收，同 SHA/同环境同覆盖 PASS 不重测；仅对修复失败项与受影响范围复验；Windows Runner 优先、真实设备专项补缺；CI 配额异常仅定向替跑缺口，不冒充 CI PASS。仓库 Actions 对 PR 执行回归，对 push 仅在 main 执行，避免同一提交因 push + pull_request 触发重复矩阵；仅文档/Markdown 变更跳过产品回归 | 减少重复验收与 Codex 额度消耗，同时保留更新/回滚、数据安全等高风险准入门槛；具体执行见 AGENTS.md |

| D022（UI V2 正式改造基线，2026-10-31） | 以用户确认的独立 HTML 交互原型 V2 作为正式 UI 改造基线；分阶段重构统一导航与工作总览、任务列表及详情抽屉、新建任务弹窗，后续再完善看板/日历/甘特图与项目视图。UI 仅重组现有数据展示，不擅自增加工时、进度百分比、任务依赖等未确认字段；保留现有任务/项目/步骤事件模型、revision/409 冲突保护、完成确认和未保存草稿保护。 | 先让用户体验可持续迭代的真实工作台界面；降低一次性大改风险，避免 UI 改造引入数据迁移或未经批准的业务扩展 |

| D023（UI V2 第二阶段只读多视图，2026-10-31） | 全部任务页面提供列表、看板、日历、日期甘特图四种只读视图，复用现有任务/项目/步骤事件模型和筛选/详情抽屉；看板不拖拽写状态，月历明确选择三个互不等价的日期字段，甘特只依据计划日／截止日期绘制显示窗口而不推断工时/进度/依赖，缺失/倒序/冲突日期单列人工核查；切换视图不得丢失未保存草稿。 | 以最小风险提供多角度任务管理，保留原业务规则、确认与冲突保护；阶段二独立分支验证后再由用户体验确认 |

当前为低复杂度个人原型。事件 JSON 中的 actor 是声明字段，不是身份认证；任何 AI 写入都不得冒充用户已确认完成。若未来要求强身份保证，需另行设计可信写入路径，不在首版临时引入复杂认证。
