# AIWorkSpace 日常工作台处理规则

> 状态：PR #54 待合并候选；合并进入 main 后成为权威规则。适用于 ChatGPT 对 AIWorkSpace 的日常业务分析、任务整理、工作记录、数据查询和数据操作；不替代代码开发规则。

## 1. 每次开始或恢复时读取，并在全过程持续遵守

- 每次**开始或恢复**任何 AIWorkSpace 工作台事务前，都必须从 GitHub 仓库 `main` 分支读取本文件的最新版本。这里的“恢复”包括：此前已讨论或执行的事项隔了几天后继续、仍在原对话中续办、换一个新对话继续，或上下文中断后重新接手。
- 不能因为事项属于“同一个任务”、原对话里曾经读过规则，或 ChatGPT 记得以前的处理方式，就跳过恢复时的最新规则读取。
- 读取规则不是一次性开场动作。事务中的查询、分析、记录、写入、复核和汇报都必须持续遵守本文件；规则一经读取，在当前连续工作时段内即时追问无需每条消息重复读取。
- **跨日恢复、切换对话／AI、上下文中断后恢复时，必须重新读取**。若在连续工作过程中发现 main 规则可能已更新，也必须在下一次写入前重新读取。
- 本文件是日常处理流程的权威入口。ChatGPT 的历史对话、项目摘要和长期记忆只能帮助理解，不能代替本规则，也不能代替当前工作台数据。
- 如果无法读取最新规则，仍可进行一般性讨论，但不得声称已按最新规则操作，也不得写入工作台数据。

## 2. 默认直接执行，不重复要求确认

- 用户清楚说明了要做什么、处理哪个对象或业务范围时，该指令就是本次操作的执行授权。先自行完成必要的查询、去重和校验，然后直接执行；不要先把常规操作拆成方案让用户再次批准。
- 不要求用户提供本可从工作台查询到的任务编号、步骤编号、字段名称或 JSON 格式。
- 只有目标存在多个无法区分的候选、缺少不可推断的必要信息、数据冲突／同步不完整、当前软件不支持该操作，或软件本身规定了额外的独立授权步骤时，才暂停受影响的写入并提出一个明确问题。
- 可以安全完成的部分先完成；不要因为一个无关字段或对象受阻而停止整个任务。
- 用户明确要求“标记完成”属于完成确认；用户只是叙述“今天做完了某件事”或要求记录工作时，只记录已发生事实，不擅自改变原任务状态。

## 3. 先判断应该使用哪个工作台模块

- **项目**：长期业务主题或工作集合。
- **任务**：未来需要执行、跟踪或确认完成的行动。
- **步骤**：某项任务内部的具体执行事项。
- **工作记录（RECORD）**：已经发生的事实，包括进展、沟通、决策／结论和随手记；不使用任务状态。
- **对象说明**：项目、任务或步骤的稳定背景、目标、范围和约束；不是工作进展，也不是工作记录。
- **总结（SUMMARY）**：对一段时间内的工作进行归纳；个人版与汇报版按当前软件规则选择来源。

不要为了记录一条进展或结论而新建步骤。不要把沟通记录写成任务状态。不要把对象说明、工作事实和未来待办混在同一个字段中。

当前 RECORD 类型为 progress、communication、decision、note。decision 的 content 用于背景／判断，outcome 用于明确结论；已有 decision 不得通过更新覆盖其核心内容，更正或新判断应新增记录。具体字段以当前代码校验规则为准。

## 4. 操作前读取真实数据

- 使用用户已授权且当前可用的 Google Drive 连接器，读取工作台实际数据；按任务名称、项目名称或用户给出的编号查询，不凭记忆定位。
- 找到对象后，使用实际存在的内部 ID；同时核实对象类型、名称、所属项目、父任务、步骤及相关工作记录。不能把显示编号、任务 ID、步骤 ID、项目 ID、记录 ID互相替代。
- 写入前读取该对象相关的完整有效事件链和当前投影，核实最新 revision、重复 event_id、关联对象是否存在、回收站状态、冲突／警告，以及是否要求 merge_basis。
- 不得只读一条旧事件就推断当前状态；不得把旧对话中的编号、状态或日期当作当前事实。
- GitHub main 的代码版本不等于用户电脑已经安装的版本。涉及新版本才支持的字段或事件格式时，先核实实际部署版本；无法核实时，不得冒险写入新格式。

## 5. 编号和字段以当前代码为准

- 每种对象使用自己的编号和校验规则。必须从当前数据中取得已有对象 ID；创建新对象时，只能按当前软件规则生成合法的新 ID 和 event_id，不能复制示例编号或自行拼接旧编号。
- 写入前只需检查本次操作涉及的当前校验函数，不要求每次通读整个代码库：
  - 任务：app.py 的 validate_event
  - 步骤：validate_step_event
  - 项目：validate_project_event
  - 工作记录：validate_work_record_event
  - 项目／任务／步骤说明：validate_object_detail_event
  - 任务与步骤转换：validate_conversion_event
  - 收件箱／总结：validate_work_archive_event
  - 异常核查审计：validate_review_event
- 不得根据业务语义自行增加字段。当前 main 的任务事件不接受 analysis、next_steps；对象说明使用独立的 object_detail_events，字段为 description；进展、沟通、决策和随手记使用独立 RECORD。未来若代码改变，以届时实际 validator 为准。
- 遇到 invalid task_id 时，先检查对象 ID 类型、字段位置、格式、父任务关系和当前数据是否存在；不能未经核查就断定任务不存在或编号是编造的。
- 遇到 unknown fields 时，定位具体对象对应的 validator，确认该事件实际允许的字段；不得靠删除、改名或猜测字段反复试写。

## 6. 写入必须遵守现有数据治理

- 只追加新的、唯一的事件文件；使用正确目录、正确事件结构、当前 base_revision 和当前要求的 merge_basis。不得覆盖、改名或删除已有事件来修复错误。
- 修改前检查重复事件和并发事件；结果不确定时先重新读取，不盲目重放。发现同一 revision 冲突、同步不完整或来源缺失时，保留原始数据并停止相关写入。
- 严格遵守 app.py 当前 validator 和 AGENTS.md 中的 Google Drive 直写安全规则。步骤 update 不得写 position；步骤排序使用独立 reorder 规则。
- 任务或步骤设为 done，必须有用户明确完成确认，并满足当前事件规则。删除步骤、任务移入回收站／恢复／彻底删除、任务与步骤转换、结束周期任务、异常修复等操作，遵守对应的明确授权和审计流程；不得绕过软件强制的独立确认步骤。
- Google Drive 上传成功不等于工作台已经读取、接受或显示该变更。不得把直接上传描述成应用 API 已校验。

## 7. 写入后必须回读验证

- 写入后重新读取新事件及相关对象投影，确认 event_id、对象 ID、revision、实际字段值和关联关系正确。
- 再检查是否出现新冲突、核查警告或同步问题。只在回读证据支持时才报告“已完成”。
- 如果文件已上传但尚未同步到用户电脑，只能报告“已写入云端／等待同步”；如果已经写入但工作台投影未接受，应报告实际阻塞，不得宣称成功。
- 不删除、不隐藏、不覆盖异常来源来让界面看起来干净。

## 8. 无法继续时的处理

说明具体是哪一个对象、哪项校验或哪种同步条件阻止了操作，以及已完成的安全部分。只问继续执行所必需的一个问题。不得编造字段、编号、状态、日期、人员、供应商承诺或写入结果。
