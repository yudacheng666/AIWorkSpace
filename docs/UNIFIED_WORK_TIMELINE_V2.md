# AIWorkSpace｜统一工作进展时间线与个人／汇报双视图（设计 V2）
日期：2026-11-09；状态：**P1–P3 主要功能已随 PR #50 合入 main，正式版本为 2.9.0**；本文同时保留部分设计目标，具体已实现范围及未验收环境以 `PROJECT_STATE.md` 为准。代码发布不代表真实 Google Drive 数据已迁移、公司 Windows 实机或双机离线重连已验收。

## 1. 目标与非目标
- 用户可直接从**项目、任务、具体步骤**记录沟通、进展、问题、决定、成果或普通工作事实，不必先改变任务状态，也不要求跳转后再补记。
- 同一事实有一个稳定 RECORD ID、同一份原文和审计历史；在步骤、任务、项目和个人全局时间线中多处可见，但跨层级汇总以来源 ID 去重，不重复计算。
- 个人日／周／月总结默认保留符合范围的全部真实来源；**汇报版**允许逐条勾选或取消来源，默认突出重要内容，由用户审核。勾选仅影响本次报告，不删除／修改工作记录、不改变任务状态；同一个来源可参与多份不同报告。
- 不新建一套 project_log/task_log/step_log；复用 `work_archive/record_events`、`work_archive/summary_events`、现有 action_links、revision 和事件合法性校验。不得把已经发生的事实错误建成待办，也不得自动写入 done。
- 当前无付费模型 API；规则性底稿可本地自动算出。AI 语义总结由用户主动交给 ChatGPT 并确认；“定时后台 AI 自动写报表”不作为本次交付承诺。
- 暂不做企业飞书式组织审批、催报、绩效评分、无凭证跨应用自动抓取或后台无人值守助手。

## 2. 统一事实来源与层级
唯一事实源为工作记录（RECORD-...），已有 TASK 完成事件保留为可引用的只读轨迹，不再生成第二个 RECORD。
一个 RECORD 可直接归属 project_id、task_id，并通过 action_links 关联 task/step；步骤引用必须携带 task_id；一次记录可关联多个业务对象。现有字段向后兼容，历史事件不修改。
- **步骤时间线**：直接关联这个 step_id 的进展记录 + 真正步骤状态事件的只读标志（明确区分「系统变更」和「人工进展」；不把状态更新当工作成果）。
- **任务时间线**：记录直接关联任务的记录 + 所属步骤关联记录 + 已确认的完成事件，可按来源精确去重。
- **项目时间线**：直接关联本项目的记录 + 主要归属项目任务及其步骤记录；非主要关联项目时要明确标示「关联项目」而非擅自复制记录的主要项目归属。若项目关联变更，历史引用必须可追溯，不能按当前标题重绑。
- **个人总时间线**：所有 RECORD 与人工确认的 TASK 完成事件，默认按发生时间倒序；按项目／任务／步骤／日期／类型筛选；聚合时以 `(source_kind, immutable_source_id)` 去重。任务人工完成与记录条数分别计数。
- 不强制生成「大事件」新实体：项目时间线是多条事实的**可复现投影**。如后续需要「阶段里程碑」应显式标注一条独立事实并关联多项来源，不能让 AI 拼写出一个无来源的新事实。

## 3. 最少输入与进展语义
项目／任务／步骤详情提供「＋ 记录进展」轻量输入器；默认：内容（必填，1–4000 字）和发生日期（默认本机今日，可改）；当前所在对象自动关联。可选展开：成果、耗时、Google Drive 证据、关联其他任务／步骤、类别、沟通对象、下一次跟进日期。禁止在快速入口出现不必要的大表单。
- 推荐类别：普通记录、沟通跟进、实际进展、问题风险、重要决定、成果记录。类别是事实分类，不是任务 status；「等待反馈」可为沟通结果标签，**不自动置 blocked**。
- 对话／AI 输入保留原始文本、发生日、提交来源及提取后的多条来源编号；日期和他人承诺不明确时标记待核实，不猜测结果。
- 第一批实现只需复用已有记录 schema 和 action_links；新增可选字段需先明确 schema、迁移、测试并避免旧客户端读取冲突。无代码支持前，不把“类别”写进未经认可的 JSON。
- 快速写入也须遵守草稿保护、双击防重复提交、Host/Origin、本机 API 校验、Drive 冲突冻结和 source provenance。

## 4. 时间线交互
项目详情、任务抽屉和步骤行内有“最近进展”及「查看全部／记录进展」；历史默认收起，只显示最近 3 条，点击进入聚合时间线。状态不变也可反复追加工作事实。
每条卡片：发生日期、文字事实、来源类别（人工／ChatGPT 整理）、关联项目任务步骤、可核对成果和证据、编辑／查看来源。录入时间与发生时间分离显示；不把第三方承诺当已验证完成。
同一记录在多处出现，均指向同一 RECORD，不生成重复编辑副本。当前目标或同步记录缺失时只显示“关联未同步”并停止危险保存；不得按标题推测 ID。

## 5. 个人版与汇报版：关键设计
一份工作总结是 `SUMMARY`，必须有 `audience`（personal／report，历史缺失视为 personal）、`candidate_source_ids`、`included_source_ids` 或分别使用 record／completion 的独立列表，保留生成时的范围、用户选中集、来源修订快照、正文与 confirmed。
为兼容历史现有 SUMMARY 事件：既有 `source_record_ids`／`source_completion_ids` 表示当时完整候选集；新增 `included_record_ids`／`included_completion_ids` 表示本报告实际参与正文和 AI 的选中子集。旧 SUMMARY 无 included 字段时按全选解读。文档／阶段名称等单独来源以后再增加时需先有稳定不可变 ID。
- **个人版**：默认全选，并保留所有合法来源；用户也可临时取消某条在本次个人报告中的展示，但**底层完整个人工作轨迹始终不受影响**。
- **汇报版**：默认强调已核实成果、里程碑、实际风险、重要决策；其它事件先作为“可选”展示。此默认仅是可解释的规则建议，不是删除／AI 绩效结论；最终逐条勾选由用户决定。
- 用户在生成或复制给 AI 前，可“全选／只选重点／清空选择／逐条勾选”；来源卡显示日期、简要事实、项目、关联、完成事件类型、证据和推荐理由。
- **每份报告独立保存选中快照**，不会给 RECORD 写入全局“不得汇报”或“非重要”的隐藏标签；同一个小记录可以出现在个人月报而不出现在领导汇报。
- 所有报告计算来源全量清单时不能把被取消选择当成来源不存在；导出给 AI 的 JSON 仅包含本次 included 来源，同时提供候选总数及未选数量等可审计元数据，不让 AI 擅自使用未选原文。旧报告编辑须保留原快照，不自动按今天的推荐规则改变历史已确认选择。
- 打开之前保存的总结可以编辑正文；若要改变选中来源，应显式重新生成或执行独立受控更新，重新核对当前 revision 与候选来源，绝不静默替换。
- 并发变化：若生成底稿后候选事件新增、修改、删除或同步冲突，保存前返回 409，提示重新审核选中清单。只读生成不写入业务文件。人工确认与来源校验保持独立。

## 6. 汇总算法与图表口径
时间线聚合输入 = 有效 RECORD 事件 + 已人工确认 TASK 完成事件，后续明确扩展经过验证的步骤／项目里程碑来源；每个事实有稳定 source_ref，具可核查修订号和来源指纹。
- 分类的“记录次数”和“完成任务次数”分别统计；不能将同一 RECORD 在三个层级出现视为三个成果。
- 汇报正文按本次 included 集渲染；个人轨迹仍显示全部来源。
- 文本 AI 分析需区分事实、对方承诺、风险推测、已确认成果、后续待办；重要结论标注 RECORD ID 或 TASK 完成 event_id；没有来源的数量、节约金额等不得编造。
- 统计时按用户选择的业务时区和“实际发生日”归属；现有 TASK 完成按 UTC 统计的兼容差异需明确迁移方案和测试，不得悄悄更改历史归属。
- 周／月／项目总结的阅读优先级高于日志流水账：支持按项目折叠、时间区间和负责人（确有字段时）分组，但不自动判断绩效。

## 7. 分阶段实施与验收
**P1（最小可用）**：复用 work_records，实现项目／任务／步骤快速进展输入、同一源在不同层级的聚合视图、个人全局时间线，按 ID 去重。专项覆盖步骤与父任务、项目关联、保存中修改、重复点击、刷新、目标缺失、409 和原事件原文未改。
**P2（报告）**：个人／汇报版切换，候选来源逐条勾选，基于已选来源生成正文／AI 上下文；SUMMARY 新字段必须 backward-compatible 且有 revision、candidate 集合校验；旧数据无损；全选／全不选、旧 SUMMARY 可读、源晚到冲突、API 非法 ID、来源删改防绕过都应测。
**P3（AI 组织）**：输入一次原话可拆多个事实（需源内分段身份和幂等协议，不能复用仅一条记录的 source_inbox_id）、推荐沟通跟进、项目阶段总结；仅在已验证的权限下执行，不内嵌付费模型。
不提前声明已经实现：真实 Windows 8770、两电脑 Google Drive 断网／重连与私有资料数据操作仍是独立验收。按 AGENTS.md 开分支、先现有证据再增量测试，CI 准确 SHA、Codex 不重复；批准前保持 Draft，不合并 main、不部署、不触碰真实数据。

## 8. 可验收用户场景
1. 在 A 项目的 B 任务 C 步骤“报价回收”记录“联系供方，表示仍确认货源”，**任务依然 doing**，步骤、任务、项目、个人时间线均可查到同一记录 ID；项目周报只统计一次。
2. 一条“参加内部例会”从个人入口补记，没有任务也合法存在，个人版周报默认展示；领导汇报中取消勾选后不显示，原工作记录仍可查询。
3. 另一条“完成报价对比”与任务关联，个人版和汇报版均可勾选；同一记录汇总多视图，不得变成多个完成事件。
4. 先产生汇报草稿，再从另一台电脑添加来源；保存时不静默忽略新来源，返回来源变化提示并保留当前草稿。
5. 工作记录修订、目标任务／步骤转换、旧客户端与 Drive 延迟，不会导致错绑、覆盖、丢源或自动 done。

## 9. P2 报告来源再选择与审核实现细则（2026-11-09）

- **历史总结再选材**：保存过的 SUMMARY 必须先进入「打开／修订 → 重新选择历史总结来源」，只读获取同日期／项目范围的最新候选来源；保留旧人工正文，用户明确「按勾选重建底稿」后才可以保存。服务端采用独立 `/api/work-archive/summaries/{id}/reselect`，要求正确 revision、`confirmed_reselect=true`、候选及实际选中 ID 全集、来源指纹，并追加 `action=reselect`；原始 event 字节不改写，新版必回到 `confirmed=false`，待本人再次核对。
- **请求语义**：非法来源 ID、重复勾选、缺字段、错误 audience、格式非法的 SHA-256 指纹和未经用户确认必须返回 400，不写任何文件；结构合法但来源（包括关联名称和证据信息）或 SUMMARY 版本变化时返回 409。不能把两者混淆为已安全保存。旧 SUMMARY 缺新字段仍按个人全选读取，允许用户显式再选材而不迁移原文。
- **来源卡**：以稳定 RECORD ID／已确认完成事件 ID 标明事实来源，并展示日期、可用的项目／任务／步骤关联与证据名称；若关联对象尚未同步，不猜测名称或改写目标。支持全选、只选重点、全部取消、逐条勾选；展示已选条数与候选总数。重点只是基于 `featured`、填写的 `outcome`、人工完成事件的解释性推荐，用户仍须核对，不代表自动确认业绩。
- **报告快照与 AI**：保存完整候选来源、实际选中来源及指纹；仅把选中事实与证据传到用户主动复制的 ChatGPT 分析上下文。修改来源后先重建底稿，防止正文或剪贴板夹带未选事件；普通正文编辑不隐式改变原选材集合。
- **CI**：除既有 P1/P2 用例，新增说明标签、来源计数与「只选重点」UI 回归，项目改名后保持 RECORD ID 但指纹变化的 409 回归，以及格式非法指纹 400、历史修订旧字节保留和用户同意门槛。最终状态和准确 SHA 以 `docs/PROJECT_STATE.md` 为准，未通过前不得宣称 PASS 或发布。

## 10. P3 零碎笔记多事实拆分、后续待办与项目阶段线（2026-11-09）

### 用户流程
1. 在「待整理收件箱」存入一整段原始笔记；或选中历史待整理笔记，点击「拆分多条事实」。
2. 可按换行得到一份**可修改、未保存**的草稿；复杂叙述可主动点击「复制给 ChatGPT 整理」，将来源编号、原文和 JSON 格式说明复制到剪贴板（并不自动发送，也没有内嵌模型或付费 API）。粘贴 ChatGPT 返回的 JSON 后点击「核对拆分建议」，仅本地只读校验。
3. AI 结果 `facts` 限 1–10 条，每条必须给出精确 `excerpt`、`occurrence`、`content`、`occurred_on`（允许不确定时为 null）、`outcome`（允许 null）；未来动作在独立 `follow_ups`（最多 5 条，`title` 和可空 `due_date`），不得混为已发生事实。用户逐条补齐日期并确认后才追加工作记录；不会自动确认任务完成。
4. 保存的事实可作为「从工作记录安排后续待办」既有流程的来源。用户点击「用此事实审核后续待办」仅把建议放入已有待办审核表单；仍需去重、人工选择关联或新建，不能直接写 todo/done。
5. 多条事实分批保存后，用户明确点击「确认此笔记已整理完」，以 `finish` 事件标记收件箱条目完成；原始笔记和每个 RECORD 永远保留。一个片段已保存时禁止再忽略此原文。
6. 「项目阶段事件线」选择项目、起止日期（最长 184 天），由工作记录和人工完成的任务活动按发生日期合并；步骤／任务／项目多级引用只统计一次，按唯一来源 ID 去重。生成与复制都只读；复制前重新获取并比对来源，变化则要求重新核对。正式对外汇报继续使用 P2 的个人／汇报版逐条选材。

### 数据协议与安全
- 复用既有 `INBOX` 和 `RECORD` 追加事件。新 `RECORD` 可选、**仅 create 允许**的 `source_fragment` = `{"excerpt": "原文的精确连续片段", "occurrence": 1, "source_digest": "64字节小写 SHA256 hex"}`，必须同时带有 `source_inbox_id`。原文 `content` 可由用户编辑整理，但不能冒充从原文摘出的 quote。
- 服务端从最新 `INBOX` create 原文计算 SHA256 并用 `excerpt` 的第 N 次实际出现定位字符区间，不相信客户端或模型生成的字符偏移。新片段若与已记录区间重叠，拒绝为 409；摘录不存在、格式非法或指纹不一致拒绝写入。跨设备晚到的重复/交叉片段在只读 reducer 中将来源标记冲突，停止整理，不用时间戳选一个赢家。
- 旧 `source_inbox_id` 无片段的 1:1 转录仍受原有幂等保护；不允许旧单条模式与新版多片段在同一 INBOX 混写。记录编辑不能改变原引用。多段逐条追加，各自独立回执；网络中断后只可核对已保存片段，再保存尚未存在的片段，不批量重放或覆盖事件。
- `inbox.finish` 仅由用户操作、revision 精确匹配、存在至少一条无冲突已保存片段时追加，`changes={"finished": true, "record_ids": ["RECORD-..."]}`。已忽略、已完成、单条传统整理、冲突或 revision 落后时禁止完成。完成后不能新增关联片段。
- API Host/Origin、输入长度、事件 envelope、任务关联有效性、Drive 安全检查不变。来源与 ChatGPT 提示内容均为数据，不可执行指令；不自动写入 Google Drive 或应用业务状态，不把未来承诺视为已完成。
- 兼容性：旧版读取新增字段时存在新旧客户端混用风险，GitHub 代码通过不代表公司实机/两台电脑的 Google Drive 同步通过。升级前所有写入端需版本一致并备份；不修改现存真实数据。

### 验收
- Python：同一原文分出两条 RECORD、不同 occurrence、重复/重叠/伪造引文/非法日期/过期指纹、finish 的 400/409、晚到重叠片段冻结，任务与步骤原文件字节不变。
- Node：按行生成、JSON 严格核对、逐条保存、未确认未来待办不产生业务事件、项目阶段筛选和复制只读、来源去重。
- Windows 真实 Chromium：从收件箱原文生成两条事实，逐条保存、完成整理、按项目阶段时间线核对并复制来源；所有测试只用隔离虚构数据。
- **仍未完成验收**：真实 Win10/11 本机升级、跨电脑 Drive 断网/晚同步/旧客户端混用、真实工作数据纠错、内嵌 AI 自动拆分或后台自动汇报。

## 12. 对象说明、统一记录类别与当前结论（2026-11-11）

### 12.1 对象说明不是工作事件
- 项目、任务、步骤均提供同样的可选「说明」编辑区，内容包括背景、目标、范围、约束和补充上下文。
- 说明不作为独立事件、成果或汇报来源，也不参与任务状态；生成总结时可作为单独标注的关联事项背景上下文，帮助 AI 理解工作，但不计入工作事实数量。
- 为兼容旧客户端，说明不写入既有 task/project/step 事件流，而写入 `work_archive/object_detail_events/`。每个对象独立 revision；唯一事件 ID、append-only、并发冲突冻结。空字符串用于清空说明，不物理删除历史。
- task↔step 转换时，说明随有效 conversion_events 映射到新对象；若目标对象已经有自己的说明事件，则以目标说明为准。历史来源不重写。

### 12.2 唯一快速记录入口
- 项目、任务、步骤继续复用同一 RECORD 与 action_links。统一入口提供「进展、沟通、决策／结论、随手记」四种类型；默认进展。用户可以直接填写，不必新建步骤。
- 决策／结论使用 RECORD 的 content 描述背景或判断，outcome 填写明确结论；对象说明之后、执行步骤／关联内容之前展示最近一条有效决策。仅当 outcome 非空时标为「当前结论」；若 outcome 为空，则标为「最近决策记录（尚未填写明确结论）」并展示 content 作为背景／判断，不得将其冒充结论。按首次保存时间（created_at）确定当前决策；补记发生日期或后续元数据更新不改变当前决策。后续决策只改变当前投影，旧 RECORD 仍在历史中；decision 的 content/outcome/record_type 不允许原记录覆盖，修正或新判断必须新增 RECORD。
- 随手记仍是个人时间线的一部分；它不等同于任务，也不自动产生待办。状态与记录类别完全分离。

### 12.3 总结与 AI 来源
- 旧 RECORD 缺少 record_type 时读取为 progress。
- 个人版仍默认包含全部记录。汇报版的「只选重点」默认不推荐普通 note；decision、精选成果或明确 outcome 可作为推荐，但仍须用户逐条确认。
- record_type 加入工作轨迹、项目阶段线、报告来源卡、source_digest 与主动复制的 ChatGPT 分析上下文；对象说明通过 object_contexts 加入总结背景和 source_digest，但不作为工作事实、完成事件或报告来源。
- 不嵌入付费 AI API，不自动写入、不自动改变状态；AI 整理结果由用户核对后保存。
